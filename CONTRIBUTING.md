# Contributing to SMuFL

This document describes how to propose a change to the SMuFL specification: adding a
glyph, adding a range, editing a description, and so on. If you want to know how the
spec is *built* (mdBook mechanics, local preview, publishing), see
[BUILDING.md](BUILDING.md) instead — this document is about making a *content* change.

## The golden rule: edit the source, never the output

```
data/ranges/*.yaml           <- you edit these
data/stylistic-sets.yaml     <- you edit this
                                          |
                                          v  tools/generate.py
                                          |
metadata/glyphnames.json     <- generated, never hand-edited
metadata/ranges.json         <- generated, never hand-edited
metadata/classes.json        <- generated, never hand-edited
mdbook/src/tables/*.md       <- generated, never hand-edited
mdbook/src/SUMMARY.md        <- the "Tables" section is generated
```

Everything under `data/` is the canonical source of truth. Everything else listed above
is a **build artifact**: it's regenerated by `tools/generate.py` and checked by CI on
every pull request. If you hand-edit a generated file, CI will catch it (your PR's
generated output won't match what you committed) and ask you to run the generator
instead.

`mdbook/src/implementation_notes/*.md` is prose and stays hand-written — the generator
only inserts an `{{#include}}` reference to it, it doesn't touch its content.

## Prerequisites

```
pip install pyyaml check-jsonschema fonttools ufoLib2
```

[Install mdBook](https://rust-lang.github.io/mdBook/guide/installation.html) if you want
to preview the built spec locally (`mdbook serve --open` from the `mdbook/` folder).

## The one invariant that matters most

**Once a glyph's name and codepoint have been merged to `gh-pages`, they can never
change again.** Its `description` can be edited freely — that's just documentation. But
the name and the codepoint are a permanent commitment: font vendors and notation
software build against them.

This is enforced automatically. `metadata/schema/check_immutability.py` runs in CI on
every PR and fails the build if a change would move or remove an existing glyph's
codepoint, or reuse a codepoint for a different name. If you hit this check, it almost
always means you should be *adding* something new rather than changing something that
already exists — see "Adding a glyph" and "A range is full" below.

## Common workflows

### Editing a glyph's description

Find the glyph in its range file under `data/ranges/<slug>.yaml` and edit its
`description` field. That's it — nothing else needs to change, and this is always safe
regardless of whether the glyph has already been published.

```yaml
glyphs:
  - name: dynamicPiano
    description: Piano   # <- edit this
```

### Adding a glyph to an existing range

Append a new entry to the end of that range's `glyphs` list in
`data/ranges/<slug>.yaml`:

```yaml
glyphs:
  - name: dynamicPiano
    description: Piano
  # ...
  - name: dynamicNewMark          # <- new entry, added at the end
    description: Some new dynamic mark
```

Codepoints are never written by hand — `tools/generate.py` assigns them by position
within the range's `codepointRangeStart`/`codepointRangeEnd` span. Run the generator
(see "Before opening a PR" below) and it'll pick the next free codepoint in that range
automatically.

**If the range is full** (no codepoints left before `codepointRangeEnd`), do not extend
the range's bounds — that's exactly what the immutability check exists to block once a
range has been published. Instead, propose a new `<name>-supplement` range (see below).

### Adding a brand-new range

1. Create `data/ranges/<your-slug>.yaml` (dash-case, matching the file naming already
   used throughout `data/ranges/`). Use an existing simple range as a template — e.g.
   `data/ranges/tuplets-supplement.yaml`.
2. Pick a free block of codepoints for `codepointRangeStart`/`codepointRangeEnd`. Look
   at `data/ranges/manifest.yaml` and `metadata/ranges.json` for the highest currently
   allocated codepoint and leave room for the range to grow — existing ranges
   conventionally pad to a round block size (see `padUpToNearest`, typically 16).
3. Do **not** set `firstPublishedIn` — omit it entirely. That field marks a range as
   already published (and therefore immutable); a new range hasn't been yet.
4. Add the file's slug to `data/ranges/manifest.yaml`, in the position you want it to
   appear in the spec's "Tables" section.
5. If the range supplements an existing one, set `supplementaryTo: <parent-slug>` (see
   below).

Minimal example:

```yaml
name: myNewRange                 # camelCase - becomes the key in ranges.json/classes.json
description: My new range
codepointRangeStart: U+XXXX
codepointRangeEnd: U+XXXX
padUpToNearest: 16
hidden: false

glyphs:
  - name: myNewRangeGlyphOne
    description: The first glyph in the range
```

### Adding a supplementary range

A `-supplement` range is how you extend a range that's already full without moving
anything in it. Set `supplementaryTo` to the *parent's file slug* (not its `name`):

```yaml
name: myRangeSupplement
description: My range supplement
supplementaryTo: my-range        # the parent's file slug, e.g. data/ranges/my-range.yaml
codepointRangeStart: U+XXXX
codepointRangeEnd: U+XXXX
```

The generator derives the cross-links in both directions automatically — the parent
range's page gets a "Supplementary Groups" section linking to yours, and your page gets
a "Supplementary to [Parent]" line. You don't add either by hand.

### Adding a glyph to a class

Add the class name to the glyph's `classes` list. The class doesn't need to be declared
anywhere else first — `classes.json` is entirely derived from what glyphs declare:

```yaml
glyphs:
  - name: accidentalFlat
    description: Flat
    classes: [accidentals, accidentals12EDOArrows]
```

### Adding a stylistic alternate

A stylistic alternate is a font-specific optional glyph (an alternate design for an
existing glyph, exposed via an OpenType feature) rather than a new SMuFL codepoint. Add
it to the range's `stylisticAlternates` list:

```yaml
stylisticAlternates:
  - for: dynamicPiano              # the base glyph's name
    name: dynamicPianoSmall        # semantic name, shown in the spec table
    set: small-staff                # references data/stylistic-sets.yaml - omit for a plain alternate
    description: Piano (small staff)
```

Omit `set` entirely for a plain, unnamed alternate — the generator assigns it
`.saltNN`, numbered automatically among that base glyph's other unnamed alternates.

The actual codepoint isn't decided in the YAML: the generator resolves it against
`metadata/font-optional-codepoints.json`, which is the authoritative record of what's
actually in the current Bravura font. If the alternate is genuinely new (not yet in the
font), the generator assigns the next free codepoint — but note that this only reserves
metadata's *expectation*; the actual glyph then needs to be added to Bravura to match
(see "How this connects to Bravura" below).

### Registering a new stylistic set

`ssNN` OpenType stylistic-set tags are shared across the *entire* font (OpenType allows
at most 20, `ss01`–`ss20`), so they're centrally registered in
`data/stylistic-sets.yaml` rather than invented per-range:

```yaml
sets:
  - id: my-new-concept
    opentype: ss11          # pick the next unused tag
    description: My new concept
```

Check `data/stylistic-sets.yaml` for which `ssNN` tags are already spoken for before
picking one. Every stylistic alternate that uses `set: my-new-concept` anywhere in
`data/ranges/*.yaml` will resolve to this same tag — that's the whole point of the
registry: one tag, one consistent meaning, everywhere it's used.

### Adding a ligature

Ligatures combine multiple existing glyphs into one optional, font-specific glyph.
List the component glyphs in order:

```yaml
ligatures:
  - name: accidentalFlatParens
    description: Parenthesised flat
    components: [accidentalParensLeft, accidentalFlat, accidentalParensRight]
```

Like stylistic alternates, the codepoint is resolved against
`metadata/font-optional-codepoints.json`, not chosen by hand.

## Before opening a PR

Run the generator and the validation checks locally — this is exactly what CI runs, so
running it yourself first means no surprises:

```
python3 tools/generate.py
find data/ranges -name '*.yaml' ! -name 'manifest.yaml' -print0 | xargs -0 check-jsonschema --schemafile data/schema/range.schema.json
check-jsonschema --schemafile data/schema/manifest.schema.json data/ranges/manifest.yaml
check-jsonschema --schemafile data/schema/stylistic-sets.schema.json data/stylistic-sets.yaml
check-jsonschema --schemafile data/schema/engraving-defaults.schema.json data/engraving-defaults.yaml
check-jsonschema --schemafile metadata/schema/glyphnames.schema.json metadata/glyphnames.json
check-jsonschema --schemafile metadata/schema/ranges.schema.json metadata/ranges.json
check-jsonschema --schemafile metadata/schema/classes.schema.json metadata/classes.json
python3 metadata/schema/check_consistency.py
python3 metadata/schema/check_immutability.py
python3 tools/sync_ufo_glyphs.py --check
```

Then build the book to confirm nothing broke:

```
cd mdbook && mdbook build
```

`git status` should show your `data/` edits plus whatever generated files changed as a
result — review that diff. If a generated file changed that you didn't expect, that's
worth understanding before you open the PR.

## How this connects to Bravura

Adding a glyph, alternate, or ligature to the YAML source describes *what should exist*
in the specification and, eventually, in the reference font — it doesn't draw anything.
`metadata/font-optional-codepoints.json` is what keeps the two in sync: it's extracted
directly from the current Bravura font, and the generator treats it as authoritative
for optional-glyph codepoints, so the spec and the font never silently disagree about
what a given codepoint means.

Two more tools close the rest of the loop, and both run in CI on every PR:

* **`tools/sync_ufo_glyphs.py`** adds an empty, correctly-named, correctly-encoded
  placeholder glyph to `font/Bravura.ufo` for anything the spec defines that the UFO
  doesn't have yet — so a new glyph in the spec always has a slot waiting for it in
  FontLab, with the right name, codepoint, and a `<note>` reminding the designer what
  it's for. It never touches a glyph that's already been drawn. Run it after adding a
  glyph/alternate/ligature:

  ```
  python3 tools/sync_ufo_glyphs.py
  ```

  CI runs it with `--check` and fails if `font/Bravura.ufo` is out of sync with the spec
  — commit whatever it adds along with your YAML change.

* **`tools/generate_font.py`** compiles `font/Bravura.otf` from `font/Bravura.ufo` using
  the open-source `fontmake` + `otfautohint` pipeline (no FontLab required), then calls
  **`tools/generate_font_metadata.py`** to produce `font/Bravura.json`, the font-specific
  SMuFL metadata file (`glyphAdvanceWidths`, `glyphBBoxes`, `glyphsWithAnchors`,
  `glyphsWithAlternates`, `ligatures`, `optionalGlyphs`, `sets`), all derived automatically
  from the compiled OTF's outlines and the UFO's own `<anchor>` elements. Both are **build
  artifacts** — gitignored, never committed. CI builds them fresh on every PR (to catch a
  UFO that fails to compile) and on every push to `gh-pages` (where they're published
  alongside the spec — see
  [about/implementations.md](mdbook/src/about/implementations.md)).

  ```
  pip install fontmake afdko
  python3 tools/generate_font.py
  ```

  `engravingDefaults` is the one section that can't be derived from the UFO — it's a set of
  hand-set design decisions (stroke thicknesses, spacing), not a property of any glyph's
  outline. Its source of truth is `data/engraving-defaults.yaml`; edit it directly if
  Bravura's engraving design changes.

* **`tools/generate_bravura_text.py`** builds `font/BravuraText.woff` — a version of Bravura
  resized and repositioned for setting inline with running text (rather than full music
  engraving), replacing the old smufl-admin FontLab/Glyphs/UFO conversion script templates.
  The largest part of what it does is generating the "combining staff position" ligatures:
  every glyph in the `combiningStaffPositions` class combined with each of the 16 staff
  position markers (`data/ranges/combining-staff-positions.yaml`) — around 15,500 glyphs,
  starting at U+F0000 (see
  [steinbergmedia/bravura#101](https://github.com/steinbergmedia/bravura/issues/101) for why).
  Per-class scale/shift rules (which glyphs get bigger, which get nudged up or down) are hand-set
  design decisions with no UFO equivalent, same as `engravingDefaults` — their source of truth
  is `data/bravura-text-transforms.yaml`.

  ```
  python3 tools/generate_bravura_text.py
  ```

  This one's slow (compiling ~19,000 glyphs plus the ligature substitution table takes a couple
  of minutes), so unlike the others it only runs on push to `gh-pages`, not on every PR.

### Font version numbering

`data/font-version.yaml` is the single source of truth for both fonts' version number (they're
always rebuilt together, so they share one). `stem` (e.g. `"1.49"`) tracks the SMuFL spec
version being worked towards — bump it to `"1.50"` (resetting `build` to `0`) only once SMuFL
1.5 is actually ready for release, as a deliberate decision. `build` increments on every
*material* change to the font — not every rebuild; a rebuild with no real design change keeps
the same number.

`tools/check_font_version.py` enforces this in CI: it hashes the actual build inputs
(`font/Bravura.ufo` — skipping empty placeholder glyphs, since adding one isn't a material
change until it's actually drawn — plus the metadata/data files that feed the font builders)
and fails if that hash changed without a version bump to match. After making a material change
and incrementing `build` (or `stem`) in `data/font-version.yaml`:

```
python3 tools/check_font_version.py --update
```

This overwrites whatever version number and copyright year FontLab last wrote into
`font/Bravura.ufo/fontinfo.plist` at build time, in both compiled fonts, so a designer
re-exporting the UFO can never accidentally change the shipped version.

### Building a full release

`python3 tools/generate_font.py --generate-release [--output-dir PATH] [--fixed-issues REF,...]`
assembles the structure found in the Bravura repository's `redist/` folder: OTF and WOFF/WOFF2
for both fonts, `bravura_metadata.json`, and an updated `FONTLOG.txt` (SVG font export is
deliberately not included — that format is deprecated). Point `--output-dir` at a checkout of
the Bravura repo's `redist/` folder to update it directly; `--fixed-issues` (comma-separated,
e.g. `steinbergmedia/bravura#101,w3c-cg/smufl#42`) fetches each issue's title via `gh issue
view` to build the changelog entry — omit it and a placeholder bullet is written instead. See
`tools/generate_release.py`.

A maintainer (or you, if you're comfortable with a font editor) still needs to actually
*draw* a new placeholder glyph in FontLab and wire up any OpenType feature it belongs
to — these tools guarantee there's a correctly-labelled slot waiting, not a finished
design.
